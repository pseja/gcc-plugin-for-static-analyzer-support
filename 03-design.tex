\chapter{Design}\label{chap:design}

This chapter details the architectural modernization of the Code Listener infrastructure.
Building upon the limitations identified in the previous chapter, the new design completely overhauls the data extraction and processing pipeline while preserving full compatibility with the existing analysis tools.

To effectively resolve the constraints of the legacy implementation, the modernized architecture was designed with five primary goals:
\begin{enumerate}
  \item \textbf{Clean Intermediate Representation (IR):} The core Code Model must remain a pure representation of the parsed program, strictly decoupling the IR from any embedded analysis results to eliminate the \uv{Large Class} anti-pattern~\cite{RefactoringGuruLargeClass}.
  \item \textbf{On-Demand Annotation Services:} The mandatory, eagerly evaluated pre-analyses must be replaced by a lazy evaluation system where auxiliary data is computed and cached only when explicitly requested by an analyzer.
  \item \textbf{Unified Exporter Pipeline:} The infrastructure must provide a uniform mechanism to export the internal representation into various diagnostic and persistent formats (such as JSON, DOT, and pretty-printed text) from a single source of truth.
  \item \textbf{Compiler and Analyzer Independence:} Strict boundary interfaces, later introduced as \texttt{IFrontend} and \texttt{IAnalyzer}, must be introduced to fully decouple the core infrastructure from both the underlying compiler and the target analysis tools.
  \item \textbf{Backward Compatibility:} Existing analyzers, specifically the Predator tool suite, must be able to operate seamlessly on the new infrastructure without requiring any modifications to their own source code.
\end{enumerate}

As illustrated in Figure~\ref{fig:new-high-level} on page~\pageref{fig:new-high-level}, the new architecture models the data flow sequentially from left to right.
The process begins with the compiler (e.g., GCC), which passes its internal representation to the Compiler Abstraction Layer.
This layer is responsible for translating the compiler-specific data into the unified, persistent Code Model housed within the Core.

It should be noted that the initial architecture was designed with a planned Model Builder abstraction layer between the GCC Adapter and the Code Model.
This was intended to elegantly decouple the incremental per-function GIMPLE translation from the flat pool structure of the Code Model.
However, as this proved unfeasible within the timeline of this thesis, the implemented architecture shown above omits this component, allowing the GCC Adapter to populate the Code Model directly.

Once the Code Model is populated, it serves as the central, immutable hub of the infrastructure.
From here, Annotation Services can dynamically augment the model with auxiliary data, and Exporters can serialize the model to disk.
Finally, execution crosses the Public API boundary, routing the model either through the Predator Compatibility Layer to service legacy tools, or through the Native Analyzer Bridge for modern, dynamically loaded analyzers.

The following sections break down each of these architectural components in detail, mirroring the flow of data through the system.

\section{Compiler Abstraction Layer}\label{sec:compiler-abstraction-layer}

The Compiler Abstraction Layer is the first stage of the processing pipeline.
Its primary responsibility is to intercept the compilation process, extract the compiler's internal representation, and translate it into a unified, compiler-independent format.
Crucially, this is the only component in the entire architecture that interacts with the underlying compiler API.\@

\subsection*{The GCC Plugin Lifecycle}\label{sub:plugin-lifecycle}

The infrastructure integrates with GCC via its standard plugin API.\@
The lifecycle begins at \texttt{plugin\_init()}, which is called when the plugin is dynamically loaded by GCC and where compiler version checks are performed.
A custom GIMPLE pass is then registered to execute immediately after the compiler's native \texttt{cfg} (Control Flow Graph) pass.
This is the same insertion point used by the legacy Code Listener.

However, the execution flow diverges significantly from the legacy architecture.
Instead of analyzing the code function-by-function during the \texttt{cfg} pass, the new design merely captures the incoming GIMPLE data.
The actual translation and subsequent analysis are deferred until the \texttt{PLUGIN\_FINISH} event, which fires only after the entire translation unit has been parsed and before GCC finalizes its internal state and finally exits~\cite{GCCInternals}.

\subsection*{Isolation and the GCCAdapter}\label{sub:gcc-adapter}

To achieve strict modularity, all GCC-specific logic is encapsulated within a dedicated compiler abstraction layer.
When the \texttt{PLUGIN\_FINISH} event is triggered, the \texttt{GCCAdapter} module performs a one-time, comprehensive translation of the GCC GIMPLE trees into the central Code Model.
Once this translation is complete, the Code Model contains no compiler-specific data.
This strict boundary ensures that no GCC-specific headers or data structures leak into the rest of the system.

Furthermore, even diagnostic reporting is abstracted.
A dedicated \texttt{GCCDiagnosticReporter} class wraps GCC's native error-reporting functions.
This ensures that any defects found by downstream analyzers are emitted with the correct file, line, and column information in the standard compiler error format, without the analyzers themselves needing to know they are running inside GCC.\@

\subsection*{Modernized Plugin Arguments}\label{sub:plugin-arguments}

The legacy configuration structures were replaced by a new, cleanly separated argument parsing architecture.
In the legacy implementation, listeners were unconditionally forced to use specific filters through a hardwired pipeline configuration.
The new design maps user arguments cleanly to optional features without hidden side effects, allowing command-line flags to specifically control the exporter and analysis pipeline on demand.

\subsection*{The \texttt{IFrontend} Strategy Pattern}\label{sub:ifrontend}

To fully decouple the analysis backend from the GCC compiler, the extraction process is generalized using the Strategy design pattern~\cite{GoF} via the \texttt{IFrontend} interface.
The \texttt{IFrontend} exposes a single virtual contract:

\begin{lstlisting}
virtual bool run(std::vector<std::unique_ptr<IAnalyzer>>&, AnalysisContext&) = 0;
\end{lstlisting}

There are two concrete implementations of this interface:

\begin{enumerate}
  \item \texttt{GCCFrontend}: Operates as the live GCC plugin, invoking the GCCAdapter to generate the model directly from memory.
  \item \texttt{JSONFrontend}: Operates as a standalone tool, reading a previously exported JSON representation of the model from disk.
\end{enumerate}

  \caption{

Once the active frontend finishes populating the Code Model, it iterates through all registered analyzers and invokes the analysis backend.
Because both frontends implement the same contract, the live compiler plugin and the offline standalone tool are completely interchangeable from the perspective of the analysis tools.

\section{Core --- Code Model and Query System}\label{sec:core}

At the heart of the modernized infrastructure is the \texttt{CodeModel}.
Once the Compiler Abstraction Layer intercepts and translates the compiler's intermediate representation, the \texttt{CodeModel} serves as the central, immutable, and parser-independent representation of the program.

\subsection*{Resolving IR Pollution and the Large Class Anti-Pattern}\label{sub:resolve-ir-pollution}

The most critical architectural shift in the \texttt{CodeModel} is its strict adherence to the Single Responsibility Principle.
As identified in the legacy architecture Section~\ref{sec:cl-architecture} on page~\pageref{sec:cl-architecture}, the original data structures, namely the \texttt{Fnc}, \texttt{Insn}, and \texttt{Storage}, suffered from severe Intermediate Representation (IR) pollution, acting as \uv{Large Class}~\cite{RefactoringGuruLargeClass} that directly embedded the results of mandatory pre-analyses such as points-to and call graphs, and also variable liveness sets.

The new \texttt{CodeModel} contains absolutely zero analysis data.
It is a pure, structural representation of the parsed source code.
By stripping out all embedded analysis fields, such as \texttt{ptg} or \texttt{callGraph}, the circular ownership and memory management complexities of the legacy design are eliminated.
Any auxiliary analysis results are now computed and managed entirely externally by the Annotation Services.

\subsection*{Entity Pools and ID-Based References}\label{sub:entity-pools}

% TODO: object pool pattern instead?
To efficiently store the program's data, the \texttt{CodeModel} employs an Entity Pool pattern inspired by Data-Oriented Design (DOD) principles.
Instead of allocating individual nodes on the heap and linking them with fragile raw pointers, the model is flattened into five central pools: types, variables, functions, basic blocks, and instructions.
These pools use \texttt{std::deque<T>} containers, which guarantee that memory addresses remain stable as the pools grow dynamically.

Entities reference each other exclusively through lightweight, strongly typed identifiers: \texttt{TypeId}, \texttt{VariableId}, \texttt{FunctionId}, \texttt{BlockId}, and \texttt{InstructionId}.
This ID-based referencing provides several major advantages: it completely eliminates the risk of dangling pointers, vastly simplifies memory ownership, and trivially enables the serialization of the entire model, such as exporting the parsed program to JSON.\@

\subsection*{Modernized Type and Instruction Hierarchies}\label{sub:type-instruction-hierarchy}

The intermediate representation models the exhaustive, closed set of types and instructions expressible in the C programming language.
To achieve safe and efficient polymorphism without the overhead of deep class inheritance and dynamic virtual dispatch, the new design utilizes \texttt{std::variant}-based wrappers.

% TODO: full list of currently available types and instructions in the appendix, maybe even some diagram?
\begin{itemize}
  \item \textbf{Type Hierarchy:} The \texttt{Type} entity acts as a wrapper over \texttt{TypeData}, which holds a \texttt{std::variant} of concrete types such as \texttt{PointerType}, \texttt{StructType}, \texttt{ArrayType}, or \texttt{VoidType}.
  \item \textbf{Instruction Hierarchy:} Similarly, the \texttt{Instruction} entity wraps \texttt{InstructionData}, a \texttt{std::variant} over operations like \texttt{AssignInstruction}, \texttt{CallInstruction}, and \texttt{SwitchInstruction}.
\end{itemize}

Notably, because the new architecture does not force hardwired filters upon the analyzer, \texttt{SwitchInstruction} is preserved natively within the \texttt{CodeModel}.
Analyzers that require raw switch semantics can now access them directly, whereas previously they were unconditionally forced to consume chains of conditional jumps.

\subsection*{The Query System}\label{sub:query-system}

Rather than introducing a separate, disjoint \uv{Query System} component, the querying mechanisms are seamlessly built directly into the public interface of the \texttt{CodeModel}.
The API provides direct $O(1)$ lookups by ID.\@
These include, but are not limited to, functions such as \texttt{getType(TypeId)} and \texttt{getFunction(FunctionId)}, alongside modern C++20 range-based traversal views.

This allows an analyzer to intuitively and efficiently traverse the control flow graph using standard range-based \texttt{for} loops.
For example, iterating over all instructions within all blocks of a function can be concisely expressed using \texttt{model.blocksOf(func)} and \texttt{model.instructionsOf(block)}.
This exposes the complex underlying data structures through a clean, highly readable interface.

\section{Annotation Services}\label{sec:annotation-services}

In the legacy Code Listener infrastructure, the \texttt{ClEasy} interface forced the unconditional execution of four mandatory pre-analyses, specifically the call graph construction, loop-closing edge detection, points-to analysis, and variable liveness, before handing control over to the analyzer.
This eager evaluation wasted computational resources and forced the core Intermediate Representation (IR) to act as a container for analysis results.

The modernized architecture resolves this by introducing a lazy evaluation system driven by Annotation Services.
In this design, the \texttt{CodeModel} remains a pure structural representation of the program, while auxiliary analysis results are computed exclusively on demand and cached externally.

\subsection*{The \texttt{AnalysisManager} and Lazy Evaluation}\label{sub:analysis-manager}

At the core of this system is the \texttt{AnalysisManager}.
Owned by the \texttt{AnalysisContext}, this manager is passed to every analyzer and exporter in the pipeline.
It acts as a type-erased cache, internally utilizing an \texttt{unordered\_map} to map unique analysis keys to instantiated annotation objects.

When an analyzer requires a specific set of data, it queries the manager using a template method, typically formatted as:

\begin{lstlisting}
template <typename T>
const T& getAnnotation(const CodeModel& model);
\end{lstlisting}

When this method is invoked, the \texttt{AnalysisManager} checks its internal cache.
If the requested annotation type \texttt{T} has already been computed, it immediately returns the cached reference in $O(1)$ time.
If it has not yet been computed, the manager invokes the static factory method \texttt{T::build(model)} to generate the data, stores it in the cache, and then returns the reference.
Because the \texttt{AnalysisManager} is shared via the \texttt{AnalysisContext}, an expensive annotation, such as a call graph, computed by an exporter can be seamlessly reused by a subsequent static analyzer without being recomputed.

\subsection*{Type-Safe Registration via CRTP}\label{sub:crtp}

To ensure type safety and eliminate the need for fragile string-based lookups or dynamic casting, the architecture utilizes the Curiously Recurring Template Pattern (CRTP).
Every annotation service must inherit from a templated base class, \texttt{AnnotationBase<Derived>}, passing its own type as the template parameter.

This CRTP base automatically injects two critical components into every service:

\begin{enumerate}
  \item A strictly enforced signature for the \texttt{build(model)} static factory method.
  \item A static \texttt{AnalysisKey} member.
    The memory address of this static member (\texttt{\&Derived::Key}) serves as the unique identifier for the type-erased cache.
    This elegant, low-overhead pattern guarantees globally unique keys per annotation type and heavily mirrors the \texttt{AnalysisInfoMixin} design found in modern LLVM~\footnote{\url{https://llvm.org/doxygen/structllvm_1_1AnalysisInfoMixin.html\#details}}.\@
\end{enumerate}

\subsection*{Implemented Services}\label{sub:implemented-services}

Currently, the infrastructure implements two primary annotation services:

\begin{itemize}
  \item \textbf{CallGraph:} This service analyzes the \texttt{CodeModel} to construct a directed graph of function invocations.
    Using Tarjan's strongly connected components (SCC) algorithm~\cite{Tarjan1972}, it computes topological orderings, identifies root functions, which are functions with no callers, and leaf functions.
  \item \textbf{SwitchToIf:} This service computes synthetic variable names and block-label allocations required to safely unfold \texttt{SWITCH} instructions into chains of conditional jumps.
    Crucially, unlike the legacy \texttt{unfold\_switch} filter, which destructively mutated the IR, this service only precomputes the textual rendering data.
    The pure \texttt{SwitchInstruction} remains perfectly intact within the \texttt{CodeModel} for any analyzer that natively supports it.
\end{itemize}

It is worth noting that the legacy pre-analyses for variable liveness, points-to graphs, and loop-closing edges were not ported as individual annotation services.
Because the modernized infrastructure preserves the purity of the \texttt{CodeModel}, advanced analyzers, such as the Predator verification kernel, prefer to execute their own highly specialized, internal versions of these analyses rather than rely on generic framework approximations.

\section{Exporters and Standalone Tools}\label{sec:exporters}

To satisfy the requirement for robust diagnostic outputs and persistent storage, the modernized architecture introduces a unified exporter pipeline.
Rather than generating outputs through disjoint, parallel listeners as the legacy system did, the new design serializes the central \texttt{CodeModel} into multiple formats, those being the DOT, JSON, and pretty printed text (PP), using a standardized, object-oriented exporter hierarchy.

\subsection*{The Exporter Base Class and Design Patterns}\label{sub:exporter-base}

All export functionality is rooted in the abstract \texttt{Exporter} base class.
This class orchestrates the export process by combining three classical design patterns:

\begin{itemize}
  \item \textbf{Visitor Pattern:} The \texttt{Exporter} inherits from a \texttt{CodeModelVisitor} interface, allowing it to systematically traverse the hierarchical structure of the \texttt{CodeModel}, those being the functions, blocks, instructions, and operands, without modifying the entity classes themselves.
  \item \textbf{Template Method Pattern:} The base class defines the overarching traversal algorithm, providing virtual hooks that the concrete subclasses override to emit format-specific output.
  \item \textbf{Strategy Pattern:} The active exporter is selected dynamically at runtime via the \texttt{AnalysisContext}.
    The export methods, specifically either \texttt{exportDot()}, \texttt{exportJson()}, or \texttt{exportPP()}, allow the infrastructure to swap export strategies seamlessly.
\end{itemize}

Furthermore, while the main analysis pipeline shares a single \texttt{AnalysisManager} instance, each concrete \texttt{Exporter} is instantiated with its own independent \texttt{AnalysisManager}.
This allows the exporter to lazily request and utilize auxiliary data, such as the \texttt{SwitchToIf} annotation, internally without polluting the primary analysis cache.

\subsection*{Diagnostic and Visual Exporters}\label{sub:diagnostic-exporters}

The infrastructure implements two exporters primarily designed for human inspection and diagnostics:

\begin{itemize}
  \item \textbf{DOTExporter:} This component generates a Graphviz \texttt{.dot} representation of the Control Flow Graph (CFG) for each parsed function.
    It is parameterized by a \texttt{DotVerbosity} flag, that allows the user to toggle the inclusion of detailed type information and unique variable identifiers.
    This fulfills the program graph visualization requirement, providing analysts with immediate visual confirmation of the extracted execution paths~\cite{CleanArchitecture}.
  \item \textbf{PPExporter:} Serving as a direct, modernized replacement for the legacy \texttt{cl\_pp} listener, the Pretty Printer exporter outputs a human-readable, three-address code (3AC) listing of the program.
\end{itemize}

\subsection*{Persistent Storage and the JSON Round-Trip}\label{sub:json-round-trip}

A major limitation of the legacy architecture was its strict confinement to the live compiler memory space.
To enable offline processing and cross-translation-unit (whole-program) analysis, the new infrastructure introduces the \texttt{JSONExporter} and \texttt{JSONImporter}.

Utilizing the \texttt{nlohmann/json} library~\footnote{\url{https://github.com/nlohmann/json}}, the \texttt{JSONExporter} serializes the entire CodeModel, including all entity pools and ID-based cross-references, into a persistent JSON file.
The \texttt{JSONImporter} performs the inverse operation, safely deserializing the JSON file back into a fully functional \texttt{CodeModel} in memory.

Because the C and C++ compilation models operate on independent translation units (source files), full verification often requires analyzing the entire program at once.
To facilitate this, the \texttt{ModelMerger} component was introduced.
It accepts an arbitrary number of deserialized \texttt{CodeModel} objects and safely merges their distinct entity pools into a single, unified whole-program \texttt{CodeModel}.

\subsection*{Standalone Tools}\label{sub:standalone-tools}

By leveraging the JSON round-trip and the \texttt{IFrontend} Strategy pattern, the infrastructure provides two standalone, offline command-line tools:

\begin{enumerate}
  \item \textbf{cl\_merge:} A utility that parses multiple \texttt{.json} files exported during a build process, invokes the \texttt{ModelMerger}, and outputs a single, consolidated JSON representation of the entire software project.
  \item \textbf{cl\_analyze:} A standalone analysis driver.
    Instead of running as a live GCC plugin, it utilizes the \texttt{JSONFrontend} to load a pre-merged \texttt{CodeModel} from disk.
    It then invokes the registered analysis backend identically to the \texttt{GCCFrontend}.
    From the perspective of the static analyzers, there is absolutely no difference between running live inside GCC or running offline via \texttt{cl\_analyze}.
\end{enumerate}

\section{Public API and Predator Compatibility Layer}\label{sec:public-api}

The final stage of the modernized architecture is the handoff to the actual static analysis tools.
To isolate the core infrastructure from the specific requirements of any single analyzer, the system exposes a strict public boundary via the \texttt{IAnalyzer} interface.

The \texttt{IAnalyzer} interface dictates a single, simple contract:

\begin{lstlisting}
virtual void analyze(const CodeModel&, AnalysisContext&) = 0;
\end{lstlisting}

The framework provides two built-in implementations of this interface that bridge the gap between the internal Code Model and the external analysis tools: the \texttt{NativeAnalyzerBridge} for modern plugins, and the \texttt{LegacyPredatorBridge} for backward compatibility.

\subsection*{Native Analyzer Bridge}\label{sub:native-analyzer-bridge}

The \texttt{NativeAnalyzerBridge} provides the integration path for new, third-party static analyzers.
An external analyzer is compiled as a shared library (\texttt{.so}) that exports a standardized C-ABI structure called \texttt{cl\_native\_analyzer\_api\_t}.
The GCC plugin loads this library at runtime using \texttt{dlopen}, which is configured via the \texttt{--load-analyzer} command-line flag.

Crucially, when the \texttt{NativeAnalyzerBridge} delegates execution to the dynamically loaded analyzer, it forwards the complete \texttt{AnalysisContext}.
This means the external analyzer has full, unrestricted access to the \texttt{AnalysisManager}; by extension, it can lazily request annotations like the \texttt{CallGraph}, use the \texttt{DiagnosticReporter} to emit compiler-formatted warnings, and also use the unified export helpers.
To demonstrate this modern capability, the infrastructure includes a reference \texttt{RecursionCheck} analyzer, that successfully uses the \texttt{CallGraph} annotation to detect cyclic function calls on demand.

\subsection*{Legacy Predator Compatibility and the Adapter Pattern}\label{sub:legacy-predator-bridge}

The most critical constraint of the modernization effort was ensuring that the VeriFIT group's primary tool, the Predator shape analyzer, continued to function without requiring any modifications to its own source code.
Predator expects its input in the form of the legacy \texttt{cl\_code\_listener} C API, which is a stream of sequential function-pointer callbacks such as \texttt{fnc\_open}, \texttt{insn}, or \texttt{fnc\_close}.

To bridge this fundamental architectural gap, the infrastructure implements the classic Adapter design pattern~\cite{DesignPatterns}.
The \texttt{LegacyPredatorBridge} instantiates a \texttt{PredatorAdapter}, which systematically traverses the new, object-oriented \texttt{CodeModel} and translates its entities back into the legacy stream of C callbacks.

\subsection*{Capability Asymmetry and the Illusion of Pre-Analyses}\label{sub:capability-asymmetry}

An important architectural asymmetry exists between the two bridges.
While the \texttt{NativeAnalyzerBridge} exposes the full \texttt{AnalysisContext} to modern tools, the \texttt{LegacyPredatorBridge::analyze()} method explicitly discards the context.
Because Predator predates the \texttt{AnalysisManager}, it cannot dynamically request framework annotations.

Instead, the \texttt{PredatorAdapter} relies solely on the \texttt{CallGraph} annotation service to determine the topological ordering of root functions (functions with no callers), ensuring they are emitted to Predator in the correct sequence.
Once the adapter fires the final \texttt{acknowledge()} callback, the handoff is complete.

This elegantly resolves the \uv{mandatory pre-analyses} problem identified in the legacy architecture.
The modernized framework no longer computes points-to sets, loop-closing edges, or variable liveness sets.
Predator's regression tests continue to pass seamlessly because the Predator kernel has always been capable of computing its own specialized versions of these analyses internally once the callback stream concludes.
The legacy framework's eager computation of these datasets was, ultimately, redundant for advanced tools.
